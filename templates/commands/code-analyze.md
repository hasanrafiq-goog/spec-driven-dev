## User Input

```text
$ARGUMENTS
```

You **MUST** consider the user input before proceeding:
- **Default (No input provided):** Run a **full repository scan**, index all files across languages, and generate the complete architectural audit and visual Code Knowledge Graph.
- **Subsystem or Keyword (e.g., `auth`, `billing`):** Perform a targeted deep-dive into the routes, models, and flow of that subsystem.
- **Specific File or Symbol (e.g., `src/core/engine.py`, `UserService`):** Calculate blast radius, trace downstream consumers, and analyze coupling.

## Pre-Execution Checks

1. Verify that `specify graph` is available by running `specify graph summary --json`.
2. Run `specify graph build` (or `specify graph build --refresh` if starting fresh or when no input is given) to ensure all source files, routes, schemas, and dependencies are indexed up-to-date.

## Execution Sequence

### 1. Full Repository Indexing & Discovery
Execute the following commands to extract the ground-truth architectural graph:
- `specify graph build`: Incrementally updates or indexes the codebase.
- `specify graph summary --json`: Extracts language breakdown, total file counts, routes, models, and symbols.
- `specify graph routes --json`: Extracts all HTTP and RPC routes across the codebase.
- `specify graph models --json`: Extracts all schemas, database tables, and entity models.
- `specify graph export --format mermaid`: Exports the complete visual dependency graph of modules, routes, and models.

### 2. Architectural Analysis & Hotspots
- **Coupling & Blast Radius Hotspots:** Identify the top 5 highest-coupling files in the repository (files with the highest count of downstream dependents/reverse dependencies).
- **Test Safety & Coverage Matrix:** Cross-reference discovered routes and data models against test files (`test_*.py`, `*.spec.ts`, `*_test.go`, etc.) to highlight untested components.
- **If user provided a specific target or subsystem:**
  - Run `specify graph query "<target>" --json` to locate matching symbols.
  - Run `specify graph blast-radius "<target>" --json` to compute direct/transitive dependents and affected endpoints.

### 3. Targeted Code Inspection (Tier 2 Retrieval)
Do NOT read entire directories into context. For the 3–5 critical anchor files identified by the graph:
- Use the exact file paths and line numbers reported by the graph to read targeted slices.
- Inspect how entrypoint routes connect to business services and database schemas.
- **Dual-Track Exploration**: The knowledge graph provides structural acceleration (routes, models, coupling, blast radius). Do not rely solely on graph results: inspect anchor files directly, read configuration files, and if `specs/` exists, cross-check whether architectural components correspond to documented specifications.

### 4. Generate the Code Analysis Artifacts

Create two artifacts:

#### A. Interactive UI Artifact
Write a rich, visual report to `<appDataDir>/brain/<conversation-id>/code-analysis.md` with:
- `ArtifactMetadata`:
  - `UserFacing: true`
  - `RequestFeedback: false`
  - `Summary`: "Full architectural health audit, system map, and visual code knowledge graph."
- **🌐 Visual Codebase Knowledge Graph**: Include the Mermaid diagram (`flowchart TD`) generated by `specify graph export --format mermaid` visualizing interconnected modules, endpoints, and schemas.
- **🏛️ Architecture Overview**: Tech stack, frameworks, detected languages, and file statistics.
- **📡 API Surface**: Table of discovered endpoints, HTTP methods, file locations, and handler functions.
- **📦 Data Models & Schemas**: Table of entities, database tables, Pydantic/Zod schemas, and fields.
- **💥 Blast Radius & Coupling Hotspots**: Top 5 highest-risk files whose changes impact the most downstream modules.
- **🧪 Test Safety & Coverage Gaps**: Matrix of tested vs uncovered routes and models.
- **💡 Actionable Insights**: Recommended refactoring candidates, circular dependency risks, or modularization opportunities.

#### B. Persistent Project Report
Save a markdown copy to `.specify/reports/code-analysis.md` in the workspace root so the team can track architecture evolution over time.
